# Drive WiFi locks locally by being the server they dial

A WiFi TTLock lock has no listening ports and no local API. It holds one long-lived outbound TCP connection to `wifilock.ttlock.com:4999`, and the cloud sends every command down it. The frames use the same V3 format as Bluetooth (`7F 5A ... CRC 0D 0A`, AES with the `lock/detail` key), with byte 10 set to the WiFi dialect marker `0x56`. So the only local way in is to be the server the lock connects to. The integration already holds every credential this needs (ADR 0003).

We run one asyncio TCP listener inside Home Assistant (`wifi_proxy.WifiProxy`). It binds on all interfaces at tcp/4999. Every config entry that turns on `wifi_local_enabled` (off by default) shares it. The user's router redirects the lock's outbound tcp/4999 to HA with a destination NAT. We do not rely on a DNS override, because the lock we tested did not use the local resolver. On each connection the listener sends the cleartext `F0` greet and reads the login reply. The reply carries the lock's MAC in the clear. The listener matches that MAC against the registered locks, in the byte order the lock sends. This is the MAC filter. The listener drops a connection that does not match. Then the entry's `cloud_enabled` option selects the mode:

- **Pass-through** (cloud on): HA opens the real cloud and answers the cloud's own `F0` with the saved login. It forwards only the cloud's first command. Once the lock's reply proves the key, HA pumps the two sockets together. HA only observes, and the TTLock app and cloud control keep working. HA does not inject commands into the live cloud stream, because that is unproven. So HA still drives a pass-through lock over the cloud. If HA cannot reach the upstream, the session falls back to takeover, so the lock stays drivable. The same happens if the upstream resolves to HA itself, which would loop.
- **Takeover** (cloud off): HA plays the cloud. It sends `F7` config and keeps the session alive with `F8` every 10 s. It serves lock/unlock, status reads and admin ops over the session.

The handshake rule depends on the op, not on the transport. We confirmed both halves against a decoded capture of the official cloud driving the lock:

- **lock/unlock**: `CHECK_ADMIN` -> fresh token -> `UNLOCK` (`0x60` on WiFi, not BLE's `0x47`) or `LOCK` (`0x58`) carrying `(token + unlockKey)` and the epoch. No `CHECK_RANDOM`.
- **admin ops**: `CHECK_ADMIN` -> token -> `CHECK_RANDOM` echoing `(token + unlockKey)` -> the op, exactly as over BLE. Without `CHECK_RANDOM` the lock declines every WiFi config op. Don't "simplify" either path to match the other.

## Considered options

- **A standalone relay outside HA**: rejected. It would need its own copy of the lock's secrets, its own lifecycle, and its own way to report state back. Inside HA, the proxy gets the credentials from the coordinator through a callable, so it never holds a stale copy. Availability and diagnostics read the same session registry. The listener starts and stops with the integration.
- **Always take over**: rejected as the default. Pass-through keeps the app and cloud features working, and still proves that the redirect works. So turning on WiFi-local changes nothing until the user turns the cloud off.
- **Always listen**: rejected. Nothing listens on tcp/4999 unless an entry asks for it.

## Consequences

- **The MAC filter identifies a lock but does not authenticate it.** The MAC is not a secret, so a peer that sends a registered MAC gets as far as the key check. Keep tcp/4999 reachable only from the network the lock is on.
- **Admission is a key proof with no decryption oracle.** AES-CBC with IV = key leaks the key to anyone who can tell whether a chosen frame decrypts. When HA holds the key, it admits an unproven peer only on the lock's exact one-block success reply. In takeover, that reply is `f7 01` to our `F7`. In pass-through, it is the reply to the cloud's first command. HA forwards only that one cloud frame before the reply, and holds the rest. HA drops up to 3 other frames before the reply, and up to 3 before the login. It does not answer or relay them, and the drop path does not depend on whether they decrypt. A fourth frame ends the connection. So does the deadline, or a close, after a dropped frame. Every such end takes one path: nothing written, no heartbeat answer, no event. Only an admitted connection replaces a lock's session. Before HA has the key (no `lock/detail` yet), it admits a matching connection unauthenticated. HA holds that connection in takeover or relays it in pass-through. HA never drives it, and it never replaces a session that proved the key.
- **After admission, a takeover frame must be one the lock sends, in its exact shape.** The allowed frames are the reply to the outstanding command, the one-byte `0x45` heartbeat, a six-byte `F1` event, and an unasked five-byte status report. The lock sends that report after a lock or unlock. A reply must echo its command. A successful reply to one of the proxy's own commands must also have the captured length. Other admin replies fit in one AES block, and paged admin reads may run longer. Any other frame ends the session by the same path. HA drops a reply that arrives after its request timed out, until it sends the next command. Once admitted, pass-through traffic is relayed unexamined.
- **Failures throttle the address.** A failed proof counts as a failure, and so does a fault after admission. Three failures within 10 minutes refuse the address for 30 s. Each further failure doubles the period, up to 15 minutes. HA forgets an address 15 minutes after its last failure or refusal. Admission clears nothing. HA holds at most 2 unproven connections per address and 4 overall, and evicts the oldest. Each handshake step has a 15 s limit.
- **Residual: the proof can be replayed.** `f7 01` is one constant block. A peer that has seen it can be admitted and impersonate the lock for a session. The checks above leave it no padding signal outside a paged admin read that the user started (list, operation log, enrolment). They also allow it only a few faults an hour. This is a protocol limit.
- **A few stray frames are tolerated.** A reconnecting lock can flush a frame buffered for its old connection, before its login or its reply. HA drops a bounded number of these, so the lock does not fail the proof and get throttled. The debug log shows the header command byte of each dropped frame.
- **The same lock in two entries stacks.** The newest registration owns the lock. HA closes the lock's live session, so the lock reconnects to the new owner. Unregistering the owner restores the previous one. Unregistering an older registration leaves the current owner alone.
- **The listener is opt-in.** It runs while at least one loaded entry has `wifi_local_enabled` on and a WiFi lock to register. It stops when the last registration goes. A bind failure raises the `wifi_proxy_bind_failed` repair issue and leaves cloud and BLE exactly as before.
- **A taken-over lock is offline to the cloud.** Cloud REST calls about it answer -3036. So the TTLock app's remote features stop, and the coordinator must not depend on them. See ADR 0005.
- **Reconnects are normal.** The lock recycles its TCP connection every few minutes. A command or read for a recent takeover client waits up to `RECONNECT_WAIT` (20 s) for the session to return. A command for a lock never seen, or seen only in pass-through, fails at once.
- **Some ops are WiFi-local only.** Fingerprint enrolment streams several scan-progress frames and needs a persistent session. BLE's one-command GATT session cannot give it that, and neither can the cloud.
- **The upstream is a hostname.** Pass-through dials `wifilock.ttlock.com:4999` (`const.WIFI_CLOUD_HOST`) for every account region. HA resolves the name at connect time. The lock resolves the same name before the redirect can catch the connection. If the name ever stops resolving, the lock finds no server. A DNS override for the name must answer only the lock's network. A global override makes HA's own pass-through resolve to itself. The proxy refuses that and takes the lock over instead.
- **No secret is logged.** The proxy logs only opcodes, statuses, battery and lock state. It never logs a key, token, proof, MAC, admin password or decoded payload.

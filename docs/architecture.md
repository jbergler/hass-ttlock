# Architecture

How the integration is wired together. Read this before editing anything under `custom_components/ttlock/`; the per-module detail lives in each file's docstring.

## Transports

The integration talks to TTLock three ways:

- **Cloud REST**: every call goes through `TTLockApi` in `api.py` (see its module docstring for auth and per-request quirks). Locks reach the cloud via a paired TTLock gateway or the lock's own WiFi radio. Full API reference: `docs/ttlock-cloud-api/` (mirrored from https://euopen.ttlock.com/document). The user picks the region (EU / International or China) in the config flow. `const.REGIONS` holds the two hosts, which differ only in hostname.
- **Local Bluetooth**: `ble.py` + `ble_protocol.py` talk to a lock directly via Home Assistant's `homeassistant.components.bluetooth`. Reads need only `aesKeyStr` from `lock/detail`. Lock/unlock and admin ops also need `lockKey` and `adminPwd` from the same response. `ble_protocol.decode_password` decodes them, so no mobile-app login is needed. Control is opt-in (`ble_control`). See `docs/adr/0003-local-ble-transport.md`.
- **WiFi-local**: `wifi_proxy.py` runs one TCP listener per HA instance on tcp/4999. It runs while at least one loaded entry has `wifi_local_enabled` on (default off) and a WiFi lock to register. A WiFi lock holds one outbound connection to `wifilock.ttlock.com:4999`. When the user's router redirects that connection to HA, the listener identifies the lock by the MAC in its login reply (the MAC filter). With the cloud on, it passes the lock through to the real cloud. With the cloud off, it takes the lock over and drives it locally. Pass-through falls back to takeover when the cloud host cannot be reached or resolves to HA itself. The frames use the same AES format as BLE (`ble_protocol.py`), with the `0x56` WiFi dialect marker. Only a takeover session can read or command the lock. A pass-through session only proves that the lock is connected. When HA holds the lock's key, a connection must prove the key before HA admits it. Every failure counts against the peer address. ADR 0004 gives the admission rules, the frame checks after admission, the backoff numbers, the connection caps, the replay residual and how two entries share a lock. See `docs/adr/0004-wifi-local-proxy.md`.

Every local credential comes from `lock/detail` (`aesKeyStr`, `lockKey`, `adminPwd`, `lockFlagPos`, `lockVersion`) plus the account `uid` from the OAuth token. `store.py` persists them on each `lock/detail` fetch, together with the non-secret detail, the passage-mode config and the credential names. It also persists the entry's key/list records and `uid` on each successful enumeration, and the gateway list on each successful gateway refresh. Setup takes the lock list from key/list. When the cloud is off or key/list fails, it takes the list from the cache. A key/list failure also raises the `cloud_unreachable` repair. Setup then restores each lock's cached credentials, detail and credential names before any per-lock cloud fetch. So both local transports keep working through a cloud outage, and across a restart during one. Only an entry that has never enumerated needs the cloud to start. ADR 0003 records why the credentials are cached.

The handshake depends on the op and the transport. Don't make one path match the other:

| | Bluetooth | WiFi-local |
|---|---|---|
| Lock / unlock | `CHECK_USER_TIME` -> token -> `UNLOCK`/`LOCK` | `CHECK_ADMIN` -> token -> `UNLOCK` (0x60) / `LOCK` (0x58), no `CHECK_RANDOM` |
| Admin ops (settings, credentials) | `CHECK_ADMIN` -> token -> `CHECK_RANDOM` -> op | `CHECK_ADMIN` -> token -> `CHECK_RANDOM` -> op |

### Transport order and the cloud toggle

- **Lock / unlock** (`coordinator._async_drive`) tries each *available* transport in the user-set `transport_order`, and stops at the first success. `transport_order` is one of the six orderings, default BLE -> WiFi-local -> cloud. BLE is available when `ble_control` is on and the radio can reach the lock. WiFi-local is available when the lock has a ready takeover session. It is also available for a recent takeover client that is reconnecting, and the command waits up to `wifi_proxy.RECONNECT_WAIT` for it. The cloud is available when `cloud_enabled` is on. The coordinator logs a transport that declines or raises, and tries the next one. If nothing is available, it raises the translated `no_transport_to_lock` / `no_transport_to_unlock`. If every attempted transport fails, it raises `lock_failed` / `unlock_failed`, which names them.
- **Admin ops** (`coordinator.async_run_local_admin_op`) run a `lock_commands` sequence over an `AdminSession`. They try BLE and WiFi-local in `transport_order`. The cloud is never interleaved. It is the caller's fallback (`services._local_first`), used only where a cloud endpoint exists and the cloud is on. `CommandRejected` means the lock answered and said no. It never falls through to another transport, and surfaces as `local_command_rejected`. A transport error moves on to the next transport, except after a non-idempotent op has been sent. Then a lost answer raises `LocalOutcomeUnknown`, and the op never runs again elsewhere. If nothing local can carry the op, the coordinator raises `NoLocalAdminTransport`. BLE admin ops also need `ble_control`. A `read_only` op holds the Bluetooth link only while its session is open. A waiting BLE lock/unlock interrupts it at its next command (`LocalReadInterrupted`), and the read moves to the next transport. A waiting write interrupts a `read_only` op on any transport at its next command (`LocalReadYielded`). The read then queues again behind the write. A background log read (`background=True`) also yields to a waiting read, and never counts as waiting itself.
- **Reads**: the fast-tier state check reads BLE and WiFi-local takeover (`wifi_proxy.async_status`, 0x14) in `transport_order`, then the cloud (`lock/queryOpenState`, only with the cloud on).
- **`cloud_enabled`** (default on). Off means zero cloud REST calls, except one key/list for an entry with no cached lock list. Setup uses the cached lock list. The poll skips the slow tier, the door-sensor checks and the cloud state read, and reads the saved settings from the lock instead (see Polling). There is no gateway coordinator. ADR 0005 covers the rest: services, the proxy mode, the webhook and the options-flow checks. See `docs/adr/0005-cloud-off-mode.md`.

## State propagation

State reaches HA four ways, merged by `LockUpdateCoordinator`:

1. **Polling**: `coordinator.py`, two tiers. The fast tier re-verifies lock state every `poll_interval` (default 30 minutes). The slow tier refreshes the ekey record, `lock/detail`, passage-mode config, the gateway list and credential names every `slow_poll_interval` (default 6 hours). The slow tier runs only with the cloud on. When the cloud is off or the `lock/detail` fetch fails, and a local admin route is up, the poll reads the saved settings from the lock instead. It reads the 0x68 switches, 0x36 auto-lock and 0x62 sound in one read-only admin op, at most once per slow interval. It merges only the fields read into the state and the cached detail. A failure keeps the previous values and never fails the poll. While a setting is unknown, a takeover session that becomes ready requests a poll. Both intervals are options, with defaults in `const.py`.
2. **Webhook push**: `webhook.py`, near-real-time. See its module docstring. Not registered while the cloud is off.
3. **Local Bluetooth read**: serves the poll's state check when the lock is in range.
4. **WiFi-local read**: in takeover, serves the poll's state check (bolt and battery). BLE and WiFi-local are read in `transport_order`, the cloud last. An unsolicited lock event on the session requests a refresh and, with the cloud off, a debounced log read. An event during a log read gets one more read after it.

A 5-minute local refresh (`LOCAL_REFRESH_INTERVAL`) reads the bolt over BLE and WiFi-local, in `transport_order`. It reads a lock only when the cloud is off or cannot reach it, and BLE or WiFi-local can. With the cloud off, an admin key and a ready takeover session, it then reads the operation log on over WiFi-local only, within the 45-second limit. A failure keeps the cache.

**Don't** collapse the webhook path in favour of "just poll faster." **Don't** speed up polling to refresh the one value BLE already gives for free: a poll fetches more than lock state. Cloud-off mode drops the webhook because it removes the whole cloud, not to swap push for polling. See ADR 0005.

## File map

- `api.py`: `TTLockApi`, the TTLock cloud REST client, plus the OAuth2 implementation classes. Exposes the account `uid` the local handshakes embed.
- `application_credentials.py`: wires up HA's `application_credentials` component for OAuth2 setup.
- `ble.py`: Bluetooth glue over `homeassistant.components.bluetooth`: presence tracking per lock MAC, the GATT session that sends one command and reassembles the reply, lock/unlock (`async_control`), and the admin-authenticated session (`async_admin_session`). All bluetooth imports are deferred and gated on the component being loaded.
- `ble_protocol.py`: the TTLock wire format as pure functions (framing, CRC, AES, `decode_password`, handshake builders, plus the feature/config/credential payload builders and reply parsers), shared by Bluetooth and WiFi-local. No I/O and no logger, because it handles key material.
- `capture.py`: `LockTrafficCapture`, the always-on per-lock ring buffer behind diagnostics. See `docs/adr/0001-per-lock-debug-capture-via-logger-hierarchy.md`.
- `config_flow.py`: OAuth2-based config flow (`TTLockAuthFlowHandler`) and the options flow (polling, Bluetooth read and control, the WiFi-local listener, transport order, cloud on/off, and the checks that refuse unreachable combinations).
- `const.py`: domain, service names, config keys, option defaults, the proxy's port and upstream host.
- `coordinator.py`: `LockUpdateCoordinator` and `GatewaysUpdateCoordinator`. `LockUpdateCoordinator` is the per-lock polling `DataUpdateCoordinator`. It merges webhook pushes and local reads, owns what `connectable` means, and holds the local credentials. It runs the transport fan-out for lock/unlock and admin ops, and computes the connection diagnostics. It keeps credential names, from the cloud and from local adds. It links the lock's device with `via_device` to the best gateway. With no gateway, it links to a device from another integration, such as a router integration, that tracks the lock's WiFi MAC. It links rather than merges, because HA never merges devices across config entries. `GatewaysUpdateCoordinator` polls TTLock gateways for online/offline status, with the cloud on only.
- `entity.py`: `BaseLockEntity`, the shared entity base most platform classes inherit from. `LockDiagnosticEntity` is the always-available base for the connection diagnostics. `local_admin_configured` gates the local-only entities.
- `lock_commands.py`: transport-agnostic admin command sequences over an `AdminSession` protocol. They cover auto-lock, lock sound, clock, passcodes, IC cards, fingerprints, the switch bitmask, passage mode writes and the operation log. One copy of each op drives both BLE (`ble.async_admin_session`) and WiFi-local (`wifi_proxy`). Pure orchestration, with no logger.
- `models.py`: pydantic v2 models for TTLock API payloads (`Lock`, `LockState`, `Passcode`, `LockRecord`, etc.). Migrated from pydantic v1. Don't reintroduce v1 patterns (`Config` class, `.dict()`, unparameterized `Optional`).
- `store.py`: `LockStateStore`, persistence in `.storage`. Per lock it holds the cached local credentials, detail, passage config and credential names (names only, never codes). Per entry it holds the key/list records, `uid` and gateways.
- `webhook.py`: receives TTLock's push notifications, shared per developer application (ADR 0002). `async_disable` unregisters it when the cloud is off and keeps the cloudhook (ADR 0005). See its module docstring.
- `wifi_proxy.py`: the in-HA WiFi listener and per-lock session registry: MAC filter, pass-through relay, local takeover (greet, config, keepalive), the command and status path, admin ops, and streaming fingerprint enrolment. It reuses `ble_protocol.py` and logs no secret values. `__init__.py` owns the lifecycle: one listener per HA instance, shared by the entries that opt in.
- `services.py` / `services.yaml`: custom service actions. The upstream actions keep their names. Where the lock can do the job, they now run locally first (`_local_first`) or take a lock-side field (`code`, `card_number`, `fingerprint_number`, `source`). Ten more are local only: `sync_clock`, `clear_credentials`, the validity and weekly-schedule actions for cards and fingerprints, `enroll_fingerprint` (WiFi-local only) and `get_lock_config`.
- `diagnostics.py`: HA diagnostics export. Redacts `TO_REDACT` keys, the Last Operator state and credential names.
- `lock.py`, `binary_sensor.py`, `sensor.py`, `switch.py`, `number.py`: entity platforms. `binary_sensor.py` includes per-lock sensors (door sensor, passage mode, the Cloud Online and Bluetooth Reachable connectivity diagnostics) and `GatewaySensor` (per-gateway online/offline, from `GatewaysUpdateCoordinator`). `sensor.py` adds the Connection, WiFi-local Link (with a `last_seen` attribute) and Credentials diagnostics. `number.py` is the auto-lock delay (seconds). `switch.py` has the auto-lock, lock-sound, tamper-alert and passage auto-unlock switches. All of these are admin-gated, and the coordinator's local-first fan-out drives them. The tamper-alert and passage auto-unlock switches are local-only, and exist only with a local admin route.
- `brand/`: local copy of the icon assets also submitted to `home-assistant/brands`.
- `translations/`: `en.json` is the source of truth. Mirror its structure when adding new strings. Don't auto-translate the other languages.
